# NCR-01: ING-10 lag over 1 s when the host is oversubscribed

- **Requirement:** ING-10 (S): at 2 × 100 Hz for 5 min the lag stays under 1 s. ATP-08 step 2.
- **What failed:** the first Gate 5 run P (`docs/perf/run-p-2026-11-18-host-load/`, 2026-11-18 17:35–17:40Z) measured a maximum time lag of **19.56 s**; the median was 23 ms. One stall, 17:40:32–17:40:53Z: the perf sampler itself has no sample for 9 s, the 100 Hz ingest worker (ingest-2) logged `Timeout reading from redis:6379` three times and the API once, and `docker stats` reported 3356 % CPU for one container on a 12-core host. The informative figures in that run failed with it (ingest p95 11.1 s, alarm p95 8.4 s).
- **Cause:** the run started 120 s after a full `make up --build` in a fresh clone; the 1-min load average before the run was **28.08** on 12 cores (2026-11-17's passing run P started at 3.73). The Docker VM was starved, and every container, the sampler included, stalled together. Redis itself logged nothing abnormal (its BGSAVE fork at 17:40:37 took 1.3 s, inside the stall, not before it).
- **Rerun under the procedure's load gate** (`docs/perf/run-p-2026-11-18/`, load 3.81 before): max lag **0.648 s**, **PASS**. The 2 h soak on the same stack (`docs/perf/soak-2026-11-18/`) lost no frame and raised no false alarm through the stall-free period and one later 2-read Redis timeout in the simulator (17:56:33Z).
- **Impact on the user:** on a ground station host that is CPU-oversubscribed, the console can show data up to tens of seconds old during a stall. No frame is lost (ING-01 held: frames wait in the stream and are acknowledged after storing), the age shown per value (UI-01/UI-03) tells the operator the data is old, and the lag clears without intervention.
- **Severity:** minor.
- **Decision:** accept with a known limitation. ING-10 is claimed for a host that is not oversubscribed; the measurement procedure now says so (ATP-08 step 0: start ≥ 10 min after a build and while the 1-min load average is under a third of the cores). Both runs stay in the record. Deployment note in the CHANGELOG known limitations: give the stack dedicated cores; the scaling path (more ingest workers, D-ING scaling row in `docs/perf/scaling.md`) does not help when the host itself is starved.

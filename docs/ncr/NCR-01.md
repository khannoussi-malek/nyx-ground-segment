# NCR-01: ING-10 lag over 1 s when the host is oversubscribed

- **Requirement:** ING-10 (S): at 2 × 100 Hz for 5 min the lag stays under 1 s. ATP-08 step 2.
- **What failed:** the first Gate 5 run P (`docs/perf/run-p-2026-11-18-host-load/`, sampling 17:39:55–17:44:55Z) measured a maximum time lag of **19.56 s**; the median was 23 ms. `lag.csv` shows two stall episodes: 17:40:04–07Z (up to 3.56 s) and 17:40:41–17:41:01Z (up to 19.56 s, decaying to 3.4 s by 17:41:01), plus a brief 1.2 s blip at 17:43:56Z; 69 of 600 samples were at or above 1 s. During the second episode the perf sampler itself has no sample for 9 s (17:40:32–41Z), the 100 Hz ingest worker (ingest-2) logged `Timeout reading from redis:6379` three times and the API once. `docker stats` reported 3356 % CPU for one container, which is impossible on a 12-core host (maximum 1200 %); it is a sampling artifact of the stall, not a measurement. The informative figures in that run failed with it (ingest p95 11.1 s, alarm p95 8.4 s).
- **Cause (probable, not proven):** the 1-min load average before the run was **28.08** on 12 cores, against 3.73 (2026-11-17) and 3.81 (the rerun) on the passing runs, and the run started shortly after a full image rebuild (`make up --build`). The aborted run N, started after the same build at load 3.55, was not slow, so the build alone does not explain it. The evidence shows a host that was oversubscribed when the run began and a stall in which every container, the sampler included, stopped together; it does not show the mechanism. Redis itself logged nothing abnormal (its BGSAVE fork at 17:40:37 took 1.3 s, inside the stall, not before it).
- **Rerun under the procedure's load gate** (`docs/perf/run-p-2026-11-18/`, load 3.81 before): max lag **0.648 s**, **PASS**. The 2 h soak on the same stack (`docs/perf/soak-2026-11-18/`) lost no frame and raised no false alarm, but it started at 17:45:08Z, right after this run, and shows a **second effect of host stalls**: at 17:56:31–33Z both vehicles showed LOSS OF SIGNAL for 2.2 s (NYX-TA1 also for 0.1 s at 17:56:28Z), 0 frames lost. In the same minute the simulator logged `tc read failed` with `Timeout reading from redis:6379` for NYX-TA1 and NYX-TA2 (compose log of the soak stack, copied before the containers were later recreated: `17:56:33.351891Z gs.simulator.commands tc read failed for NYX-TA1: Timeout reading from redis:6379` and `17:56:33.391228Z … tc read failed for NYX-TA2: Timeout reading from redis:6379`). The ground saw more than 2 s without frames, so the LOS was a correct detection of a host stall, not a false limit alarm, and every frame was stored. An operator would have heard a LOS tone during a nominal run.
- **Impact on the user:** on a ground station host that is CPU-oversubscribed, the console can show data up to tens of seconds old during a stall. No frame is lost (ING-01 held: frames wait in the stream and are acknowledged after storing), the age shown per value (UI-01/UI-03) tells the operator the data is old, and the lag clears without intervention.
- **Severity:** minor.
- **Investigation (owner asked for a fix before v1.0):** [stall recovery trials](../perf/stall-2026-11-18/summary.md). After a 10 s freeze of the whole stack at 2 × 100 Hz the lag is back under 1 s 2.5–3.5 s after resume (3 trials), on the unchanged code. The slow recovery in the failed run is the simulator's catch-up burst draining on a starved CPU: with ingest capped at about 0.25 core per worker it takes about 10 s, as in the failed run. No ingest defect was found, so no code changed.
- **Decision (accepted by the owner, 2026-11-18, after the investigation):** accept with a known limitation. ING-10 is claimed for a host that is not oversubscribed; the measurement procedure says so (ATP-08 step 0: start ≥ 10 min after a build and while the 1-min load average is under a third of the cores). Both runs stay in the record. Deployment note in the CHANGELOG known limitations: give the stack dedicated cores; the scaling path (more ingest workers, D-ING scaling row in `docs/perf/scaling.md`) does not help when the host itself is starved. A cheaper per-frame storage path would shorten the drain on a loaded host; it is not part of v1.0.

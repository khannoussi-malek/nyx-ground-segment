# Extensions Review: GS-EXT-01..04 (design §11)

Independent review of `docs/design.md` §11 (GS-EXT-01..04, D-EXT-01..19, ATP-E1..E4) and the core decisions §11 changed (D-SIM-04/11, D-ING-18/21, D-ALM-02/11/12/13, D-CMD-03/09, D-DB-03/11, D-REP-01/05, §3, §3.2 DDL, §5). Checked against the spec (§2 personas, §3 interfaces, §4 pass conditions), `docs/requirements.md` §4.7 and the rows that cite D-EXT, and `docs/assumptions.md` A-EXT-1..16. Both earlier design reviews were read for context only.

## 1. Verdict

**PASS WITH CONDITIONS.** No extension changes a spec pass condition on paper. The file-name decision (A-EXT-1), `limits_sha256` = `sha256sum mission/limits.yaml`, the "only shorter" timeout rule and the deadband floor in every check set all keep ALM-01/02/08 and CMD-02/03 literally intact. Four MAJOR findings remain. One is in the Gate 2 core and has to be fixed before Gate 2 closes: a generated file that depends on `mission/parameters.yaml` turns CI red on every "add a parameter" commit (EX-01). The other three come after the 47 and have to be fixed before that extension is built: export running inside the live API process (EX-02), out-of-range calibration silently dropping alarms (EX-03), and a chaos invariant that a correct system breaks (EX-04). The four small Gate 2 loader and DDL fixes (EX-05..EX-08) also belong in the thin slice.

## 2. Answers to the five questions

1. **No harm to the core.** On paper the core is safe: ALM-08's "alarm shows file hash" is met literally (D-EXT-02), CMD-02 can't be lengthened (D-EXT-07), ALM-02 holds per set (D-ALM-02 floor "in every check set"), and the shipped `commands.yaml` has no `allowed_modes` (A-EXT-7). Four things do touch must paths in practice. A stale-checked generated frame schema couples ENG-06 to `make gen` from Gate 2 (EX-01). Export runs GIL-bound in the process that serves live SSE (EX-02). A derived expression that raises turns every frame into a poison DLQ entry through D-ING-04 (EX-11). The extension build changes the engine and replay code after acceptance without re-running the ATPs (EX-16). Replay and determinism (DAT-06, D-REP-05) stay sound, because mode comes from the frame and the set switch is keyed by `LIMITS_APPLIED`. Two gaps remain there: derived values for DUP_OR_LATE frames are undefined (EX-13), and the hash on the alarm row no longer identifies everything that produced the alarm (EX-10). `isolate_valve` can't be blocked as shipped, but nothing prevents a later edit from doing it, and the API reads mode from *stored* telemetry, so an ingest outage would block it too (EX-14).
2. **Core from Gate 2.** The `mission/` format and the `check_set` column are justified: ALM-08, CMD-03 and D-DB-11 need the registry and the catalogue from the first worker on, and initdb runs once. The column could equally come later through `gs-migrate` (EX-21), but it costs nothing. The full codegen chain does not belong in a 6 h thin-slice gate: `datamodel-code-generator` with base-class injection, Redocly HTML, committed generated files, the duplicates meta test and `frame.mission.schema.json`. Only the shapes of the frame, DLQ and SSE models need deciding early (EX-15).
3. **Pass conditions.** EXT-01 (b), (d), (e), (f) and EXT-04 (b), (d) are measurable and have deterministic tests. Weak spots: the EXT-01 (a) test checks only `git diff src/` and can't see EX-01. EXT-02 (a) uses a p95 of 20 samples, which the design itself says is too few (EX-18). EXT-02 (b) has no case for an hour whose schema changed (EX-19). EXT-03 (b): invariant I7 is broken by the soak's own worker hang (EX-04), and the action counts don't fit the stated schedule (EX-17). Running the soak nightly plus once on the reference machine is a sound evidence plan, provided "green" is defined without I4 on hosted runners (EX-27).
4. **Over-engineering.** The 30-line evaluator is the right size. Simpler options exist for these: pydantic-first models exported to JSON Schema instead of `datamodel-code-generator` (EX-15), no Redocly at Gate 2 (EX-15), the table calibration form only (EX-22), no `frozen_check` flag (EX-23), and no REST-vs-OpenAPI contract test (EX-24).
5. **Security and safety.** The AST whitelist blocks code execution, but it has no length, depth or integer limits and no catch-all, so a valid-looking expression can raise into the frame path (EX-11). Derived-to-derived cycles are blocked for `expr` but not for `rate_of` (EX-12). The YAML loading is unspecified: PyYAML keeps the last of two duplicate keys without an error, accepts anchors and aliases, and has no size cap (EX-05). A calibration table can hide the most abnormal readings (EX-03). Any hot reload can flip `hazardous` with no "who" recorded (EX-25).
